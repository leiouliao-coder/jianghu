# M1 · 持久化与事务内核 验证记录

日期：2026-10-16。范围：开发计划M1。**这不是游戏验收**：本阶段建立的是服务端资产账本，尚无对外的账号或游戏接口，16项可玩验收仍全部待执行。

## 产物

- 依赖：`github.com/jackc/pgx/v5 v5.11.0`（2026-09-07发布，用户已批准）。
- `server/internal/store`：
  - 内置SQL迁移，用咨询锁防止多个进程同时迁移。
  - `Do`：带`request_id`的请求事务。
  - 账号、角色（每号最多6个）、背包、节点仓库及其他容器。
  - 物品发放与移动、钱币发放与移动。
- 数据表：`accounts`、`characters`、`containers`（钱币是容器内的实物数量，约束`coins >= 0`）、`items`（每行一个堆叠，只属于一个容器）、`requests`、`events`。
- 服务端启动：设置`JIANGHU_DATABASE_URL`后，启动时校验数据、连接数据库并迁移，任一步失败即以退出码1停止；不设置时只提供诊断接口。
- `server/compose.yaml`：本机开发用PostgreSQL 16，只监听127.0.0.1。
- CI：加入PostgreSQL服务，并设置`JIANGHU_REQUIRE_DB=1`，数据库测试不能被静默跳过。

## 规则如何实现

| 规则（基线§4.1） | 实现方式 |
|---|---|
| 同一请求重放返回原结果，不重复扣或产 | `requests`表以`request_id`为主键。结果先查表；并发的首次执行中只有一个能写入请求记录，其余回滚后读取已存结果 |
| 请求ID被挪用 | 账号、类型或载荷的SHA-256任一不同，返回`ErrRequestMismatch` |
| 规则拒绝也是确定结果 | 业务函数在保存点内执行；被拒绝时回滚它已做的写入，只记录拒绝结果；之后重放返回同样的拒绝 |
| 临时故障可安全重试 | 数据库错误整体回滚、不记录，客户端可以用同一ID重试 |
| 物品位置唯一 | 先锁容器，再按`id`和来源容器锁定物品行；物品已不在来源容器就拒绝（`not_here`） |
| 资金不为负 | 扣款用条件更新`coins >= 金额`，数据库`CHECK (coins >= 0)`作为最后一道防线 |
| 容量与负重 | 移入前先检查格数（每个堆叠占一格，钱币按每格10000计）；背包另查负重`(80+臂力)` |
| 不死锁 | 涉及的容器按ID升序一次性加锁 |
| 可追溯 | 每次成功修改都写入`events`，并关联到对应请求 |

## 测试证据

本机PostgreSQL 16.15（临时实例），Go 1.25.6 darwin/arm64，`go test -race`连续3轮通过。

| 测试 | 结论 |
|---|---|
| `TestConcurrentPickupExactlyOnce` | 50个账号同时拾取同一把剑：只有1个成功，49个收到`not_here`；剑只在胜者背包里；移动事件只有1条 |
| `TestConcurrentCoinsNeverNegative` | 1000钱，50个请求各取30：恰好33个成功、17个余额不足；剩余10；钱币总数守恒；直接写入负数会被数据库拒绝 |
| `TestConcurrentLastSlot` | 只剩1格的容器，50个物品同时放入：只有1个成功 |
| `TestReplayAppliesOnce` | 同一请求重放100次加并发20次：只入账一次，事件只有1条，每次返回相同结果 |
| `TestConcurrentDuplicateFirstAttempt` | 30个并发请求争抢同一请求ID的首次执行：只生效一次 |
| `TestCharacterLimitUnderConcurrency` | 同一账号并发建10个角色：恰好6个，背包也是6个 |
| `TestRequestMismatch`、`TestRejectionRollsBackAndIsReplayed`、`TestTransientErrorIsNotRecorded`、`TestBackpackWeightAndSlots`、`TestMigrateIsIdempotent` | 通过 |

变异检查（逐项故意改坏代码，确认测试会失败，改完后恢复）：

| 改动 | 结果 |
|---|---|
| 去掉“物品必须在来源容器”的条件 | 50个请求全部拾取成功，测试失败 |
| 去掉余额检查 | 多扣的请求被数据库约束拦截，测试失败 |
| 去掉容器加锁 | 14个物品同时放进了最后一格，测试失败 |

第三项起初没有被测试抓到，因为测试里的并发请求很少真正重叠。为此加了测试专用钩子`raceWindow`：在“检查”和“写入”之间短暂等待，让并发请求必然重叠。正式运行时这个钩子什么都不做。

端到端：真实进程连接测试库，迁移成功，`/healthz`返回200；第二次启动不重复迁移（迁移记录仍为1条）；收到SIGTERM后正常退出（退出码0）；数据目录错误或数据库不可达时以退出码1停止。
