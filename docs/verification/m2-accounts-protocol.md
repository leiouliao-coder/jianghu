## 规则如何实现

| 规则 | 实现方式 |
|---|---|
| 同号只有一个角色在世界（基线§4.1） | 每个账号一个租约，记录哪个角色、由哪个连接控制。另一个角色要进入会被拒绝（`character_present`），错误里会指出在场的是哪个角色 |
| 断线不能借机换角色 | 断线后角色保留30秒（`world.json`，安全区规则）；这期间只能重连原角色。旧连接迟到的断线事件不会影响已接管的新连接 |
| 别处登录 | 新登录或令牌恢复会踢掉旧连接（关闭码4001）；角色仍在世界中，新设备可以接管原角色 |
| 不暴露账号是否存在 | 账号不存在、密码错误、令牌无效，三者返回完全相同的`bad_credentials`；账号不存在时也执行一次等量的哈希运算；同一连接失败5次后断开 |
| 建角色不重复执行 | 复用M1的请求幂等，按账号区分`req_id`；同一`req_id`换了内容会被拒绝 |
| 连接安全 | 单条消息上限64 KiB；拒绝二进制帧；`req_id`限1–64个可打印ASCII字符；60秒无消息断开；每个连接单独一个写线程，发送队列满时断开（4004）；关停时先通知所有连接，最多等10秒 |

## 测试证据

本机PostgreSQL 16.15（临时实例），Go 1.25.6 darwin/arm64，Godot 4.7.2 macOS。

| 测试 | 结论 |
|---|---|
| `ws.TestAccountAndCharacterFlow` | 注册、重名、非法名字和密码、登录、重复登录、建角色、列表、进入未知角色、已有角色在场时换角色被拒、离开、换角色、他人角色不可进入 |
| `ws.TestKickAndSingleCharacter` | 第二处登录：旧连接先收到`kicked`推送，再以4001关闭；另一个角色进不去，原角色可以接管；离开后可以换角色 |
| `ws.TestDisconnectLingerThenSwitch` | 网络中断后，保留期内换角色被拒；保留期结束后可以换 |
| `ws.TestBadCredentialsAreUniformAndLimited` | 账号不存在与密码错误的回复字节完全相同；伪造令牌被拒；达到上限后以4002关闭 |
| `ws.TestResumeWithToken` | 凭令牌恢复会话成功，并踢掉旧连接 |
| `ws.TestCharacterCreateIsIdempotentAndLimited` | 同一`req_id`重放返回相同结果；换内容被拒；重名被拒；第7个角色被拒 |
| `ws.TestProtocolErrors` | 非JSON、超长`req_id`、未知类型、空payload、二进制帧都返回错误；版本不符时以4003关闭 |
| `ws.TestIdleTimeoutAndLongLivedConnection` | HTTP服务器读写超时设为300毫秒时，长连接仍然可用；空闲超时后断开 |
| `ws.TestShutdownClosesConnections` | 关停时连接以1001关闭，关停后新来的连接也会立即被关闭 |
| `session.*` | 并发50个角色争抢进入，只有1个成功；迟到的定时器不会释放已重连的角色 |
| `auth.*` | 哈希格式、每次加盐不同、错误格式被拒、名字规则（含中文；拒绝空格、表情符号、尖括号） |
| Godot `test_protocol`、`test_account`、`test_bootstrap` | 离线测试全部通过 |
| Godot `smoke_ws`（连真实服务端） | 注册→登录→建角色→列表→进入→第二处登录踢掉第一个连接（4001）→接管原角色→离开。连续3次通过 |

`go test -race`覆盖`ws`、`store`、`session`，连续3轮通过。

变异检查（逐项故意改坏，确认测试会失败，改完后恢复）：

| 改动 | 结果 |
|---|---|
| 不踢旧连接 | 两个测试失败 |
| 允许同号多个角色同时在场 | 三个测试失败 |
| 不限制登录失败次数 | 测试失败 |

其中一项检查发现了多余代码：我原本在升级连接前手动清除HTTP超时，但删掉后测试仍然通过。查Go源码确认，`net/http`在升级连接（hijack）时已经自动清除超时，于是删掉了这段多余代码，对应测试保留。

## 发现的问题

1. **Godot `WebSocketPeer`会丢掉关闭前的最后一条消息。** 服务端先发`kicked`推送、再发关闭帧，两者在同一轮读取中到达时，Godot直接进入“已关闭”状态，前面的消息丢失（用调试脚本实测确认）。关闭码4001每次都能收到。处理方式：协议里规定以关闭码为准，关闭前的消息只是尽力送达；客户端根据4001提示“账号已在其他设备登录”。没有在服务端加延迟来绕过，因为那样依赖时序，不可靠。
2. **客户端原先只在连接“打开”时才读取消息。** 已改为不论连接处于什么状态，都先把收到的消息读完。这个改动本身正确，但解决不了第1条，因为那是引擎内部丢弃的。

## 未验证与限制

- 只有明文`ws://`；正式环境必须使用`wss://`（TLS），尚未实现。
- 登录失败次数按连接计数，断开重连就会重新计数；按IP或按账号的限流尚未实现（上线前必须补上）。
- 在场租约保存在内存里：服务端重启后租约清空，目前也没有持久的世界状态需要保护。分区进程化时必须改为共享存储。
- 移动端：没有做真机测试；iOS/Android对明文`ws://`的限制尚未验证。
- 账号界面没有做人工视觉验收；触屏操作方案（开放问题Q1）仍未设计。
- GitHub Actions的端到端任务只在本地模拟过，远程运行结果以GitHub实际状态为准。
